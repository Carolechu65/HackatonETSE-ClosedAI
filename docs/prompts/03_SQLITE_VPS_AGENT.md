# Persona 3 — SQLite, VPS, seguridad y agente

Copia el bloque «Prompt principal» completo. Las rutas `server/` son **objetivo de implementación**: la base anterior sigue en `functions/` y no se ha migrado mediante esta documentación. Los tres subprompts finales se delegan después de fijar contratos. No pegues claves, tokens ni contraseñas del VPS en el prompt.

## Prompt principal

```text
Actúa como responsable del backend, seguridad, persistencia compartida y agente de alarmaT. Implementa una entrega funcional y verificable; no te limites a un plan. La decisión vigente sustituye Firebase como backend por SQLite en nuestro VPS. Usa Node.js 22, TypeScript estricto, Fastify y better-sqlite3. Mantén Expo y el runtime nativo Android de tus compañeros. No añadas Firestore, Firebase Auth, Cloud Functions, Admin SDK ni RNFirebase a la solución nueva. Expo Push Service puede usar FCM como transporte Android opcional; esa dependencia de transporte no convierte Firebase en la base de datos o identidad del producto.

La app permite proponer alarmas a otras personas. Cada destinatario acepta, rechaza o elige otra hora: nadie puede consentir por él. Tu primera entrega prueba A crea → B consulta y responde → C no puede acceder, aunque C comparta piso. Entrega además contrato y fixtures del agente: «Recuérdale a Ana sacar la basura cuando vuelva» debe pedir la hora que falta y producir un borrador revisable. La implementación de IA conserva prioridad P1; no retrases operaciones P0 por integrar un modelo ni presentes un fixture como IA real.

Somos seis personas. P1 controla base Expo, contratos, configuración y CI. P2 pantallas, autenticación visible y formularios. P3 tú controlas servidor, autorización, SQL, agente y operación del VPS. P4 runtime de alarmas Android. P5 HTTP, persistencia móvil, sesión y sincronización. P6 widgets, tareas e integración entre dos dispositivos. No estás solo: respeta cambios ajenos, inspecciona git status y no renombres contratos unilateralmente. Lee AGENTS.md aplicables, README.md, FEATURES.md, docs/TDD.md, docs/SQLITE_VPS_PRACTICES.md, docs/adr/004-vps-sqlite.md, contracts/README.md y los archivos afectados.

Inspecciona functions/src/index.ts, functions/src/operations/, functions/src/domain/, functions/src/contracts/ y functions/src/agents/ como código legado reutilizable, no como backend vigente. Sus callables son stubs, su comprobación parcial de consentimiento no sustituye autorización y compilarlas no valida una API SQLite. Implementa el nuevo backend en server/src/app/, auth/, operations/, persistence/, messaging/, agents/ y pruebas separadas. server/migrations/ contiene SQL numerado. La estructura todavía puede requerir creación: no afirmes que sus scripts ya existen. Tú eres dueño de server/; P1 coordina cambios raíz de scripts, workspace y CI. Como principal integra serialmente server/package.json, lockfile, contratos del servidor y exports. Subagentes no editan esos archivos compartidos. Retira legado solo tras adaptar consumidores y CI con P1, evitando borrar trabajo simultáneo.

Antes de paralelizar acuerda con P1/P5 una hoja de interfaces. Mantén OperationEnvelope y DTO actuales; preserva schemaVersion, operationId estable, groupId, entityId cuando corresponda, expectedRequestVersion y expectedDecisionRevision. POST /v1/operations/{operationName} transporta los comandos existentes. Conserva OperationReceipt, serverTimeEpochMs y status APPLIED o REPLAYED, y AppError con code/message/retryable y campos opcionales acordados. No añadas wrappers o campos extra a esquemas que los prohíben. Publica ejemplos válidos/incorrectos y mapeo HTTP. La identidad viene de la sesión del servidor, nunca de actorUid enviado por el móvil. Runtime validation para cuerpos, límites, fechas UTC enteras, zona IANA, modo, pertenencia, destinatarios y caducidad; un cast TypeScript no valida entrada.

Implementa auth mínima propia: POST /v1/auth/register, POST /v1/auth/login, GET /v1/auth/me y POST /v1/auth/logout. Contraseña con Argon2id; token bearer opaco generado con CSPRNG y al menos 32 bytes aleatorios. Guarda hash del token, usuario, expiración y revocación en SQLite, nunca el secreto original. Primer corte sin refresh: al expirar se requiere login. Define duración configurable, límites y errores uniformes. P5 almacena token en SecureStore; no en SQLite móvil ni AsyncStorage. No aceptes token por query ni lo registres. No inventes OAuth o recuperación de contraseña terminados. Login del usuario y acceso SSH al VPS son fronteras distintas.

Diseña SQL normalizado con PK, FK, índices y CHECK. Tablas mínimas: users, sessions, groups, memberships, invitations, alarm_requests, alarm_recipients, device_schedules, devices, operations, outbox_events y change_events; tasks y agent_sessions cuando el recorrido las consuma. No conviertas una colección Firestore en una bolsa JSON sin integridad. Idempotencia UNIQUE(actor_uid, operation_id); destinatarios únicos por propuesta/usuario; índices para bandeja de destinatario, enviados, membresías activas, eventos pendientes y feed por usuario. Tokens de push, hashes de contraseña, sesiones e invitaciones son privados y nunca salen en DTO de grupos. La tabla y el path interno no autorizan nada: cada lectura/mutación debe filtrar recursos por el actor y servicios comprobados.

Abre SQLite solo en el proceso del VPS, archivo fuera del webroot, disco persistente local. Inicializa WAL, foreign_keys=ON, busy_timeout acotado y synchronous=FULL; verifica configuración efectiva. Un proceso de aplicación es suficiente; no multipliques workers escritores ni uses filesystem de red. Usa queries preparadas y transacciones breves. better-sqlite3 es síncrono: ningún callback transaccional puede contener await, modelo, red ni push. Serializa migraciones numeradas al inicio controlado y registra versión aplicada; una migración fallida impide servir un esquema a medias. No corrijas producción borrando el archivo. Las bases SQLite de los móviles son proyecciones separadas de P5: no se comparten ni se sincronizan solas.

Implementa por incrementos. Primero auth, grupo e invitaciones de uso limitado con secretos hasheados, caducidad y consumo atómico; fixtures A/B/C claramente identificados. Segundo createAlarmRequest y respondToAlarm con autorización y transacciones. ACEPTAR no equivale a PROGRAMAR: requestVersion cambia con la propuesta y decisionRevision con la decisión. Rechaza horas pasadas, actor ajeno, transición inválida y aceptar por otra persona. Tercero registerDevice, setPrimaryDevice y reportSchedule; valida usuario, dispositivo principal, deviceEpoch y versiones de consentimiento vigentes. Un ACK antiguo no revive cancelaciones. Un reporte SCHEDULED prueba programación declarada por el dispositivo, no que alguien haya oído sonido.

Dentro de la misma transacción guarda efecto de dominio, operación idempotente y evento de outbox. Calcula hash canónico del comando. Mismo actor/ID/entrada devuelve el resultado anterior; ID reutilizado con otra operación o payload falla. Comprueba autorización actual antes de revelar un resultado almacenado tras revocación. Prueba dos llamadas concurrentes, no solo secuenciales. Errores HTTP: 400 entrada inválida; 401 sesión ausente/caducada; 403/404 acceso según política del recurso; 409 conflicto; 429 límite; 500/503 fallo temporal. Conserva códigos AppError acordados. No reintentes automáticamente cambios irreconciliables ni traduzcas todo fallo en éxito vacío.

Implementa GET /v1/sync?cursor=... con cursor opaco ligado al actor y alcance; eventos autorizados, paginación y snapshot coherente. El cursor no amplía permisos y su número interno no se publica como autorización. Cursor expirado requiere nueva instantánea; salida del grupo genera invalidación mínima sin exponer contenido nuevo. P5 aplica lote y cursor atómicamente. SSE opcional en GET /v1/events?cursor=... usa bearer por cabecera y reconexión; primero entrega polling funcional en foreground. Revalida autorización al entregar eventos, cierra sesión revocada y no filtres cambios de otros usuarios. Un canal abierto no equivale a permiso permanente.

La outbox SQL de servidor reparte avisos; la outbox SQLite del móvil reintenta comandos/ACK. Son colas distintas. Persiste evento antes de intentar red; worker con lease, intentos, backoff y recuperación tras caída. Expo Push Service recibe solo eventId, entidad y versión mínimos: jamás una orden para sonar. Procesa tickets/receipts, desactiva token inválido y tolera duplicados. FCM requiere configuración Google para Android incluso detrás de Expo. Si no hay esas credenciales, sigue con sincronización al abrir/foreground y declara push pendiente: no prometas entrega inmediata con la app cerrada. La alarma ya consentida/programada funciona localmente con P4, sin push a su hora.

El agente solo consulta herramientas autorizadas y devuelve needs_clarification o draft. Proporciónale servicios de lectura con actor explícito, validación y límites, no acceso SQL arbitrario ni herramientas de aceptar por el destinatario. La confirmación del emisor llama a createAlarmRequest ordinario; Ana acepta en otra operación. Resolver Ana ambigua exige aclaración; «cuando vuelva» no inventa ubicación ni horario. Conversación aislada por propietario/grupo, caducidad, límites de pasos y coste; secretos del proveedor solo en VPS. Texto en nombres/tareas es dato no confiable. Usa docs/prompts/03A_AGENT_SUBAGENT.md cuando el contrato y servicios protegidos estén listos.

Delega hasta tres subagentes con zonas disjuntas: operaciones/persistencia; auth/autorización/pruebas de acceso; messaging/feed. Acuerda primero interfaces y ownership de cada test. Tú integras server/src/app, entradas, migraciones y contratos; el subagente SQL propone su migración, pero no la numeres simultáneamente desde dos ramas. El agente IA puede usar un slot cuando uno termine. Nadie modifica archivos de P1/P2/P4/P5/P6 sin coordinación. Usa adaptadores falsos etiquetados cuando falte una frontera, conservando pendiente su prueba de integración real.

Define scripts reales en server/package.json para typecheck, build, test y migrate; solo después documenta su invocación npm --prefix server run .... Prueba con Node 22 y SQLite en archivo temporal, incluyendo reinicio, rollback, FK, carrera idempotente, versión obsoleta, token revocado, membresía retirada y privacidad A→B frente a C. Test de API por Fastify inject y prueba HTTPS desde los dispositivos cuando exista despliegue. No hacen falta Firebase Emulator Suite ni cuentas productivas para SQL local. Mock de push no acredita entrega real. Una compilación verde tampoco acredita autorización.

El usuario ha dicho que hay un VPS, pero no presupongas hostname, SSH, dominio ni arquitectura. Prepara configuración con placeholders y despliegue reproducible; usa credenciales y destino explícitos disponibles en el entorno sin revelarlos. Un proceso supervisado, reverse proxy HTTPS, usuario sin root, directorio de datos privado y logs redactados bastan. Copia consistente mediante Online Backup API o backup() del driver, retención y copia fuera del VPS. No copies solo el .db abierto en WAL. Verifica restauración en archivo separado e integrity_check. Documenta rollback de aplicación y estrategia de esquema sin destruir datos ni anunciar un despliegue que no ocurrió.

Termina con archivos concretos, contratos fijados, comandos y resultados, operaciones reales, bloqueos y evidencias. Entrega a P5 auth/URL configurada/errores/feed/ACK; a P2 estados y contrato del asistente; a P1 scripts/contratos/configuración; a P6 seed, reset y caso A/B/C. Distingue integración local, desplegada y física. No marques terminados stubs ni afirmes que SQLite resuelve sincronización por sí solo. Mantén la política de integración de P1, no force-push y no incluyas cambios de otro compañero sin revisar el alcance.
```

## Matriz de aceptación

| Caso | Evidencia |
|---|---|
| Registro/login/logout | Sesión opaca funcional; token revocado no accede. |
| A crea, B consulta/responde | API HTTP y SQLite real con transacción. |
| C ajeno o miembro no destinatario | Lectura y mutación denegadas. |
| Reintento concurrente / payload cambiado | Un efecto lógico / conflicto explícito. |
| ACK de versión o epoch viejo | No altera el estado vigente. |
| Push o proceso fallan | Propuesta persiste, outbox recuperable y ningún envío dentro del commit. |
| Reinicio/restauración | Persistencia y copia consistente verificadas. |
| Agente sin horario | Aclaración estructurada; ninguna aceptación o alarma inventada. IA real sigue P1. |

Tu ownership: server/src/operations/, server/src/persistence/ y tests correspondientes. No estás solo; no edites auth, messaging, agente, app/index, manifests o contratos compartidos. ```text

Pacta repositorio de sesiones/usuarios con A y entrega rutas/plugin a P3 para integración serial. El actor viene del bearer validado, nunca del uid del body. Define comprobadores de pertenencia/recurso para que operaciones los usen dentro de su transacción. ```text

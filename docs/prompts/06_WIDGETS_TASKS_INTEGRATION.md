# Persona 6 — Widgets, tareas e integración

Copia el bloque «Prompt principal» en tu agente. Los subprompts posteriores son encargos que ese agente puede repartir. El reparto sigue la numeración original de START_HERE: P6 cubre widgets, tareas e integración.

## Prompt principal

```text
Lee también nevera-retro.md, la guía visual incorporada al repositorio. Aplica sus tokens y componentes a tu área, coordinando los recursos compartidos con P1/P2. Adapta los ejemplos web a React Native o al widget sin copiar APIs CSS incompatibles; conserva accesibilidad y estados reales. La guía visual no amplía el alcance funcional acordado.

Eres la persona 6 de alarmaT, aplicación Android hecha con Expo, React Native, TypeScript y Firebase. Trabaja en este repositorio hasta entregar un widget real con próxima alarma, propuestas pendientes y acceso a las decisiones del destinatario, además de una tarea básica vinculable. La interfaz debe mostrar lo que el sistema ha confirmado: aceptar no equivale a programar. Nuestro diferencial es poner alarmas a otras personas conservando su consentimiento.

No estás solo en el código. Hay seis responsables: P1 base/contratos/CI/configuración, P2 pantallas/navegación, P3 backend/seguridad/FCM y agente, P4 runtime Android, P5 datos/sincronización y P6 tú, widgets/tareas/integración/demo. No reviertas cambios ajenos ni modifiques las zonas de otros sin acordarlo. Puedes delegar trabajo acotado usando los tres subprompts de este documento; informa de archivos exclusivos y dependencias antes de comenzar. No delegues el mismo archivo a dos agentes ni crees coordinadores adicionales.

Lee primero AGENTS.md si existe, README.md, FEATURES.md, docs/TDD.md, docs/TEAM_PLAN.md, docs/START_HERE.md y docs/ANDROID_PRACTICES.md. Inspecciona src/widgets/snapshot.ts, src/widgets/README.md, src/features/tasks/model.ts, TaskPreview.tsx, src/domain/alarms.ts y package.json. La estructura actual tiene una proyección pura del widget y una tarea de demostración; todavía no instala un widget Android. expo-widgets no está instalado en la base inicial. Comprueba el estado actual antes de asumir que sigue igual.

Tus zonas de implementación son src/widgets/, src/features/tasks/ y docs/demo.md. Los tests de estas áreas también son tuyos. P1 integra package.json, lockfile y app.config.ts; P2 integra las rutas de app/ y pantallas compartidas. P5 controla repositorios, SQLite, bootstrap y sincronización. P3 implementa operaciones y autorización de tareas. P4 implementa la programación nativa. Entrega a cada responsable una propuesta concreta de contrato o parche; no copies su implementación dentro de tu módulo para avanzar aparentemente más rápido.

Empieza por un recorrido vertical pequeño. Con un usuario autenticado, una alarma confirmada y una propuesta pendiente, el launcher muestra la próxima alarma futura y el contador correcto. Pulsar una propuesta abre su pantalla y permite aceptar o cambiar hora mediante el flujo compartido. Si no hay sesión, se solicita acceso antes de cargar contenido privado. Después añade tareas básicas: título, responsable válido del grupo, fecha de activación opcional, vencimiento opcional y estado. No añadas gastos, huchas, calendario externo ni un editor visual de widgets.

Acuerda con P5 un WidgetSnapshot versionado y acotado al usuario y grupo, con fecha de generación, próxima ocurrencia realmente programada, propuestas pendientes y activaciones pendientes. La firma actual de buildWidgetSnapshot es un punto de partida: los enums simplificados del scaffold no cubren todos los estados del TDD. No inventes un segundo modelo incompatible. Solicita a P1/P5 la ampliación compartida necesaria y usa un adaptador explícito mientras se integra. Una propuesta rechazada, caducada, cancelada o sin confirmación local de programación no puede aparecer como alarma activa. El receptor puede mostrar una alarma programada localmente cuyo acuse remoto siga pendiente; no confundir ese estado con la vista confirmada del emisor. Inyecta el reloj para ordenar y filtrar fechas de forma reproducible.

Verifica en documentación oficial la API de expo-widgets compatible con la versión fijada de Expo. Pide a P1 instalar y configurar únicamente las dependencias necesarias, con development build reconstruida. El runtime del widget es separado: no presupongas hooks React, acceso directo al contexto de sesión, SDK Firebase, SQLite abierta por la app ni ejecución de promesas arbitrarias. Renderiza desde una proyección persistida/publicada mediante una API verificada. Mantén la selección de datos pura y separada de la plantilla del widget.

Los botones del widget pueden abrir deep links autorizados para ver, aceptar o cambiar hora. Abrir una ruta con parámetros nunca significa consentimiento. La pantalla carga la entidad vigente, comprueba la sesión y pide la acción explícita correspondiente. Un ID en un enlace no autoriza lectura ni mutación. No ejecutes una escritura crítica desde un callback que solo funciona con el proceso React vivo. Si la librería ofrece acciones directas utilizables, demuéstralas en dispositivo y acuerda con P5 cómo entran en el mismo flujo idempotente; el primer corte puede usar exclusivamente deep links.

Define la política de actualización con P5: cambios de proyección, reconciliación al abrir/reanudar, decisiones confirmadas y retirada de sesión/grupo deben publicar un snapshot nuevo cuando la plataforma permita ejecutar ese trabajo. No prometas refresco inmediato por FCM ni un timer continuo. Muestra cuándo se actualizó la información si puede estar obsoleta. Si el teléfono está offline, una cancelación remota puede no haber llegado. No presentes un estado viejo como confirmación actual. Al cerrar sesión, limpia el snapshot privado y muestra un estado vacío; en cambio de cuenta no reutilices datos del usuario anterior.

Para tareas, sustituye demoTask por componentes que reciben datos y acciones de un puerto acordado con P5. Los datos simulados siguen etiquetados como demo hasta conectar el repositorio. Usa las convenciones del TDD para UID, tiempo, versión e IDs; el modelo inicial assignedTo no debe convertirse en un nombre libre como identidad. Crear/completar/cancelar tareas se envía por la vía de operaciones P3/P5. No escribas Firestore desde la pantalla. Completar una tarea invalida sus alarmas vinculadas en servidor y los dispositivos las cancelan al reconciliar; muestra retirada pendiente cuando falta acuse. Posponer/detener una alarma nunca completa por sí solo la tarea.

Trabaja en tres incrementos integrables: 1) proyección pura y contrato de enlaces; 2) widget instalado y pantalla de tarea conectable; 3) estado real, limpieza de sesión y recorrido con dos dispositivos. Antes de bloquearte por otra área, prepara adaptadores de prueba claramente identificados, fixtures y evidencia de lo que falta. No marques como real una integración simulada.

Prueba casos que detecten errores: alarma aceptada con permiso pendiente; dos próximas alarmas desordenadas; ocurrencia pasada; empate estable; rechazo/cancelación; snapshot antiguo; cambio de usuario; enlace a entidad inexistente o ajena; completar tarea dos veces; completar tarea con receptor offline. Los tests deben comprobar comportamiento y fronteras de autorización, no duplicar literalmente el algoritmo. Integra el runner elegido por P1; no añadas otra pila de tests solo para este módulo.

Ejecuta npm run typecheck y las pruebas disponibles de tu área. Una exportación JS no demuestra que el widget exista. Registra modelo/API de Android, build, pasos, fecha y resultado de instalar, añadir al launcher, actualizar y abrir enlaces con app cerrada normalmente. Distingue proceso cerrado de forzar detención desde ajustes. Si no tienes dispositivo o build, entrega código y pruebas que sí puedas correr, dejando explícita la validación física pendiente.

Al cerrar cada incremento, entrega archivos modificados, comportamiento conseguido, comandos ejecutados/resultados, límites y handoff concreto. P1 recibe configuración y resultados para CI; P2 recibe rutas; P5 recibe contrato de snapshot y eventos; P3 recibe campos/operaciones de tareas y coordina contigo el guion del agente. Tú reúnes la evidencia de integración y demo: cada responsable conserva la obligación de probar su área, no concentres toda la QA en P6. Prepara docs/demo.md con un guion de tres minutos y un registro de build, dispositivos, pasos y resultados: propuesta, aclaración del agente cuando esté disponible, revisión, aceptación, widget y sonido. Coordina la parte agéntica con P3 y las pantallas con P2. Incluye reinicio de datos y un caso de rechazo; distingue grabación, simulación y ejecución real. No anuncies «terminado» porque compile: la primera entrega exige widget instalado con estado real y acceso al flujo de decisión.
```
